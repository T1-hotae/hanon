# 문무니(Munmuni) 프로젝트 개요

> 이 문서는 "문무니는 무엇이고, 누구를 위해, 어떻게 동작하는가"를 정리한 프로젝트 전반 설명서입니다.
> UI/디자인 시스템은 [DESIGN.md](DESIGN.md), 실행·배포·세팅 절차는 [README.md](../README.md)를 참고하세요.

---

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 팀명 | 무니네 |
| 서비스명 | **문의할게 무니? — 문무니** |
| 한 줄 소개 | 강남대학교 재학생을 위한 **문의 중심 학사 안내 웹서비스** |
| 형태 | 학생용 웹(React SPA) + 교직원용 관리자 데스크탑 앱(Tauri, 별도 저장소) |
| 마스코트 | 양 "문무니" — 검색·채팅·안내 전반의 화자 역할 |

문무니는 학사 정보를 **찾아 헤매는 경험을 질문 한 줄로 대체**하는 서비스입니다.
학생은 주제를 고르지 않고 바로 질문하고, AI가 학교 자료(FAQ·공지·체크리스트·부서 연락처)를 근거로 답합니다.
AI가 확신하지 못하는 질문은 **상담사 전용 채팅**으로 연결하고, 전화가 더 빠른 문의는 **부서 번호를 바로 연결**합니다.

핵심 진입점은 홈 화면의 검색창 하나입니다. 검색창 제출은 검색 결과 페이지가 아니라 `/chat?q=...`로 이동해
**"검색 = 챗봇에게 질문하기"** 가 되도록 설계했습니다 ([HomePage.tsx:21](../src/pages/HomePage.tsx#L21)).

> **네이밍 참고** — 저장소 안에는 초기 이름인 "학사 한눈에"가 [README.md](../README.md)와
> AI 시스템 프롬프트([api/chat.ts:50](../api/chat.ts#L50))에 남아 있습니다. 현재 정식 서비스명은 **문무니**입니다.

## 2. 문제 정의

> 흩어진 학사 정보와 질의응답 게시판의 복잡한 접근 경로 때문에 학생은 원하는 정보를 찾기 어렵고,
> 관리자는 같은 문의를 반복 응대하고 있다.

### 2.1 학생이 겪는 문제

- 공지가 여러 곳에 흩어져 있고 홈페이지 구조가 복잡해 원하는 정보를 찾기 어렵다.
- 질의응답 게시판의 **존재나 위치 자체를 모른다.**
- 게시판에 답이 있어도 **비밀글이 많아** 남의 답변을 참고할 수 없다.
- 결국 전화 문의로 몰린다.

### 2.2 관리자(교직원)가 겪는 문제

- 답변을 작성해도 비밀글이라 공유되지 않아 **같은 질문이 계속 반복**된다.
- 전화 문의가 많아 동일한 내용을 반복 안내해야 한다.
- 어떤 문의가 얼마나 들어오는지 **집계된 근거가 없다.**

### 2.3 목표

1. 학생은 원하는 정보를 **질문 한 번으로 빠르게** 찾는다.
2. 관리자는 **반복 문의를 줄여** 업무 부담을 낮춘다.
3. 문의를 **데이터로 남겨** 무엇이 반복되는지 관리자가 알 수 있게 한다.

## 3. 타겟층

### 3.1 핵심 사용자 — 강남대학교 재학생

| 구분 | 내용 |
| --- | --- |
| 대상 | 강남대학교 재학생 (학부 재학·휴학·복학 예정자 포함) |
| 관심 주제 | 전부전과, 수강신청, 휴학·복학, 장학, 졸업요건 등 **학사 행정** |
| 사용 상황 | 시즌별 학사 일정(전부전과·수강신청·휴학 신청 기간 등)이 다가올 때, 관련 정보를 빠르게 확인하거나 문의하기 위해 접속 |
| 사용 기기 | **모바일 우선.** 강의 사이 이동 중 스마트폰으로 확인하는 상황을 기본 시나리오로 잡고, 480~960px 구간을 촘촘히 대응 (§[DESIGN.md 반응형](DESIGN.md#반응형-브레이크포인트)) |
| 기술 수준 | 특별한 사전 학습 없이 쓸 수 있어야 한다. **가입·로그인 없음**(익명 인증) |
| 심리 상태 | "전화하기는 부담스럽고, 게시판에 글 남기고 기다리기는 답답하다" — 즉시성과 낮은 진입 장벽이 핵심 |

**대표 사용 시나리오**

1. 전과 신청 기간이 다가와 검색창에 "전과 자격"을 입력한다 → AI가 FAQ·공지를 근거로 답한다.
2. 답을 받았지만 본인 학점이 애매하다 → `상담사 연결`을 눌러 학번·학과·이름을 입력하고 상담사 채팅을 연다.
3. 지금 통화가 더 빠를 것 같다 → 부서 전화번호 안내에서 학적팀 번호를 눌러 바로 전화한다.

### 3.2 두 번째 사용자 — 학사 담당 교직원(관리자)

| 구분 | 내용 |
| --- | --- |
| 대상 | 학적·수업·장학 등 학사 문의를 응대하는 교직원 |
| 사용 도구 | **별도 관리자 데스크탑 앱**(Tauri, `han-non-e-admin`). 이 저장소는 학생 웹 + 공용 API만 담는다 |
| 하는 일 | 카테고리·FAQ·체크리스트·공지·부서 연락처 등록/수정, 상담사 채팅 응대, 문의 통계 확인 |
| 인증 | Firebase Authentication **이메일/비밀번호** 로그인. 학생(익명)과 보안 규칙 수준에서 분리 ([firestore.rules:10](../firestore.rules#L10)) |
| 기대 효과 | "매번 입력하고 매번 답변하기" → "확인하고 승인하기"로 역할 전환 |

### 3.3 명시적 비대상

- 교외 사용자(입시 수험생·학부모) — 학사 행정 재학생 문의에 범위를 한정합니다.
- 개인 학적·성적 조회 — AI는 개별 확인이 필요한 질문을 답하지 않고 상담사로 넘깁니다
  ([api/chat.ts:57](../api/chat.ts#L57)).
- 학사 안내와 무관한 일반 대화 — 정중히 거절하도록 프롬프트에 명시했습니다.

## 4. 기존 방식과 문무니

| | 기존 (학교 홈페이지 + 전화) | 문무니 |
| --- | --- | --- |
| 정보 찾기 | 메뉴 여러 단계를 거쳐 공지 검색 | 검색창에 질문 한 줄 → AI가 근거를 모아 답변 |
| 게시판 접근 | 경로가 복잡하고 존재를 모르는 학생도 많음 | 홈 첫 화면이 곧 문의 진입구 |
| 남의 질문 참고 | 비밀글이 많아 불가 | 자주 묻는 질문(FAQ)·인기 공지를 홈에 공개 |
| 해결 안 될 때 | 전화 대기 또는 게시판 작성 후 무기한 대기 | 상담사 채팅 즉시 개설 + 부서 번호 원터치 연결 |
| 로그인 | 포털 로그인 필요 | **불필요**(익명 인증) |
| 관리자 | 같은 답변 반복 작성 | 반복 문의 감소 + 문의 통계 자동 집계 |

## 5. 핵심 기능

### 5.1 AI 학사 상담 챗봇

- 주제를 고르지 않고 자유롭게 질문하면, **전체 학사 자료**를 근거로 답합니다.
- 근거 자료: `faqEntries` · `notices` · `checklists` · `contacts` · `categories`
  ([ChatPage.tsx `buildKb`](../src/pages/ChatPage.tsx#L217)).
- 자료에 없는 내용은 지어내지 않고, 확신이 낮으면 `confident=false`로 응답합니다.
- 응답은 JSON 스키마로 강제(`answer` / `confident` / `relatedNoticeIds`)해 파싱 실패를 없앴습니다
  ([api/chat.ts:100](../api/chat.ts#L100)).

### 5.2 상담사 연결 (핸드오프)

- `confident=false`면 "상담사 연결을 눌러 주세요" 안내를 자동으로 덧붙입니다.
- `상담사 연결`을 누르면 **학번·학과·이름**을 받고 **상담사 전용 새 대화**를 엽니다.
  AI 대화를 승격시키지 않고 별개 대화로 만들어, 두 대화가 섞이지 않게 했습니다
  ([ChatPage.tsx `submitEscalation`](../src/pages/ChatPage.tsx#L374)).
- 입력값은 [studentIdentity.ts](../src/utils/studentIdentity.ts) 한 곳에서 정제·검증하고,
  [firestore.rules](../firestore.rules#L78)에서 한 번 더 검사합니다(브라우저 검증 우회 방어).

### 5.3 실시간 채팅 및 대화 기록

- 로그인 없이 **익명 인증**(`signInAnonymously`)만으로 대화를 만들고 실시간으로 답변을 받습니다.
- 내 대화 목록·메시지는 Firestore `onSnapshot`으로 실시간 구독합니다.
- 좌측 기록 패널에서 `전체 / AI 채팅 / 상담사 채팅`을 구분해 지난 대화를 이어볼 수 있습니다.
- `기록 초기화`는 실제 삭제가 아니라 `hiddenForStudent` 플래그입니다 — 관리자 쪽 상담 이력은 보존됩니다
  ([chatService.ts:239](../src/services/chatService.ts#L239)).

### 5.4 문의 통계 분류

- 대화의 **첫 질문**을 그 대화의 대표 문의로 삼아 `inquiries`에 기록합니다.
  문서 id를 `conversationId`로 고정해 대화당 문의가 정확히 하나만 남습니다
  ([inquiryService.ts:155](../src/services/inquiryService.ts#L155)).
- 1차 분류는 클라이언트 키워드 매칭(`detectCategory`, [constants.ts:39](../src/constants.ts#L39)).
- 2차 분류는 관리자 앱에서 호출하는 **AI 주제 분류 API**([api/admin/classify.ts](../api/admin/classify.ts)) —
  같은 의도의 질문을 하나의 `topic`/`topicKey`로 묶어 문의 추이를 볼 수 있게 합니다.
  기존 주제 재사용을 규칙으로 강제해 주제가 무한히 늘어나는 것을 막습니다.

### 5.5 부서 전화번호 안내

- 학내 부서 연락처를 그룹(학사·장학·복지 등)별로 분류하고 부서·업무·번호로 검색합니다.
- `tel:` 링크로 바로 통화 연결되며, 누른 기록은 `source: 'phone'` 문의로 집계됩니다
  ([DirectoryPage.tsx:56](../src/pages/DirectoryPage.tsx#L56)).
- **개인 실명은 담지 않고** 부서·업무·내선만 노출합니다([academic.ts:101](../src/types/academic.ts#L101)).
- 원본 데이터는 [number_collect.md](../number_collect.md)(2026년 7월 기준 구내전화 안내)에서 정리했습니다.

### 5.6 홈 화면

- 히어로 검색창이 곧 챗봇 진입구 → `/chat?q=...`
- 카테고리 카드 클릭 → **신청 전 체크리스트 모달**(진행률 표시 + `AI에게 물어보기`)
- `많이 찾는 검색어` — 채팅 첫 화면의 추천 질문과 **같은 목록을 공유**([constants.ts:11](../src/constants.ts#L11))
- `지금 많이 묻는 질문` — `faqEntries` 중 `showOnHome`이 켜진 항목(관리자가 지정)
- `자주 찾는 원문 공지` — 조회수 상위 10건

## 7. 시스템 구성

```
[학생 브라우저]  React 18 + Vite + TS (SPA)
      │
      ├─ 읽기/쓰기 ──────────► Firebase Firestore
      │                        (categories, faqEntries, checklists, notices,
      │                         contacts, departments, inquiries, conversations/messages)
      ├─ 익명 인증 ──────────► Firebase Authentication (signInAnonymously)
      │
      └─ POST /api/chat ─────► Vercel Serverless Function ──► OpenAI API
                               (OPENAI_API_KEY는 서버에만 보관)

[관리자 데스크탑 앱]  Tauri + React (별도 저장소 han-non-e-admin)
      ├─ 이메일/비밀번호 인증 ─► Firebase Authentication
      ├─ 읽기/쓰기 ──────────► Firestore (전체)
      └─ POST /api/admin/classify ─► 문의 주제 AI 분류 (Bearer 토큰 검증)
```

### 7.1 기술 스택

| 영역 | 사용 기술 |
| --- | --- |
| 프런트엔드 | React 18, TypeScript, Vite, React Router 6, CSS Modules |
| 데이터 | Firebase Firestore (실시간 구독), Firebase Authentication |
| AI | OpenAI Chat Completions, 기본 모델 `gpt-4o-mini`(`OPENAI_MODEL`로 변경) |
| 서버(BFF) | Vercel Serverless Functions (`api/`), `firebase-admin`으로 관리자 토큰 검증 |
| 배포 | Vercel(웹 + API), Firebase(규칙·인덱스) |
| 품질 | `oxlint`, `tsc -b` (빌드 시 타입 체크) |

### 7.2 설계 원칙

1. **Firestore 단일 소스** — mock 폴백을 두지 않습니다. 데이터가 없으면 빈 상태로 표시해
   "가짜 데이터가 진짜처럼 보이는" 상황을 막습니다([academic.ts:114](../src/types/academic.ts#L114)).
2. **카테고리는 하드코딩하지 않는다** — 관리자가 추가한 카테고리가 자동 반영됩니다.
   예약어 `etc`(기타)만 catch-all로 관례 사용.
3. **API 키는 절대 클라이언트에 두지 않는다** — `OPENAI_API_KEY`에 `VITE_` 접두어 금지.
   `/api/chat` 프록시만 키를 읽습니다.
4. **AI 대화와 상담사 대화는 끝까지 분리** — 한 대화의 `needsHuman`은 생성 후 바뀌지 않습니다.
5. **검증은 한 곳에, 확인은 두 번** — 식별정보 규칙은 `studentIdentity.ts` 한 파일,
   실제 차단은 클라이언트 + `firestore.rules` 양쪽.

정의는 [src/types/academic.ts](../src/types/academic.ts)에 모여 있습니다.

| 컬렉션 | 내용 | 읽기 | 쓰기 |
| --- | --- | --- | --- |
| `categories` | 학사 항목(전과·수강신청·휴학 등) + 문의처·운영시간 | 공개 | 관리자 |
| `faqEntries` | 자주 묻는 질문/답변, `showOnHome`, `viewCount` | 공개 | 관리자 (학생은 `viewCount`만) |
| `checklists` | 항목별 '신청 전 체크리스트' | 공개 | 관리자 |
| `notices` | 원문 공지(제목·링크·게시일·조회수) | 공개 | 관리자 (학생은 `viewCount`만) |
| `contacts` | 부서 연락처(부서·업무·내선·그룹·우선순위) | 공개 | 관리자 |
| `departments` | 학과 목록 + 별칭(상담사 연결 폼 선택지) | 공개 | 관리자 |
| `inquiries` | 문의 집계(`source: chat\|phone`, `categoryId`, `keyword`, `status`) | 관리자 | 학생은 `pending` 생성만 |
| `conversations` | 대화 메타(식별정보, `needsHuman`, 읽음 플래그, 제목) | 본인 또는 관리자 | 본인/관리자 |
| `conversations/{id}/messages` | 메시지(`from: student\|ai\|bot\|admin`) | 본인 / 관리자(단, `ai` 제외) | 학생은 student·bot·ai, 관리자는 admin |

### 8.1 권한 설계에서 의도한 점

- **상담사는 AI 대화를 볼 수 없습니다.** `conversations` 읽기는 `needsHuman == true`인 대화로 제한하고,
  메시지 읽기에서도 `from == 'ai'`를 제외합니다([firestore.rules:97-118](../firestore.rules#L97-L118)).
  AI와 나눈 대화가 상담사에게 그대로 노출되지 않도록 DB 수준에서 막은 것입니다.
  (규칙은 필터가 아니므로 관리자 앱 쿼리도 같은 조건을 걸어야 합니다.)
- **학생은 자기 대화만** — `studentId == request.auth.uid`.
- **삭제는 관리자만** — 학생의 '기록 초기화'는 숨김 처리입니다.

## 9. 주요 동작 흐름

### 9.1 질문 → AI 답변

1. 홈 검색창 제출 또는 채팅 입력 → `/chat?q=...`
2. 학사 자료 로딩 완료를 기다린 뒤 새 대화 생성(`createConversation`) — 자료 없이 첫 답변이 나가는 것을 막습니다.
3. 학생 메시지 저장 → 첫 질문이면 **대화 제목 저장 + 카테고리 추정 + `inquiries` 기록**.
4. `POST /api/chat`에 `kb`(전체 학사 자료) + 최근 10턴 히스토리 전송.
5. 응답을 `from: 'ai'` 메시지로 저장. `confident=false`면 `from: 'bot'` 안내를 덧붙임.
6. 실패 시에도 대화가 끊기지 않게 "상담사 연결을 이용해 주세요" 안내를 저장합니다.

> Firebase가 설정되지 않은 환경에서는 `LOCAL` 데모 모드로 동작해 화면 확인은 가능하지만,
> 기록 저장·상담사 연결은 비활성됩니다.

### 9.2 상담사 연결

1. `상담사 연결` 클릭 → 학번(9자리 숫자)·학과(`departments` 매칭)·이름(한글 2~6 / 영문 2~30) 입력.
2. 필드별 검증(blur·제출 시점). 학번 입학연도가 어색한 경우는 **경고만** — 편입·재입학을 막지 않습니다.
3. 검증 통과 시 `createHumanConversation`으로 **상담사 전용 새 대화** 생성(`needsHuman: true`),
   어느 AI 대화에서 넘어왔는지 `sourceConversationId`로 추적.
4. 안내 메시지를 남기고 그 대화로 화면 전환. 학생이 실제로 문의를 남기면 `unreadForAdmin`이 올라갑니다.

### 9.3 문의 통계

1. 학생 첫 질문 → `inquiries/{conversationId}` 생성(`status: 'pending'`, 1차 키워드 분류).
2. 전화번호 클릭 → `source: 'phone'` 문의 추가.
3. 관리자 앱이 `POST /api/admin/classify`를 호출 → AI가 `topic`/`topicKey`로 묶어 반환.
4. 관리자가 카테고리·주제별 문의 추이를 확인.

## 11. 남은 문제와 고도화 계획

### 11.1 남은 문제 — 공지 등록이 여전히 수작업

지금 관리자는 학교 공지를 한 건씩 손으로 옮깁니다. 제목·링크·카테고리를 매번 입력해 공지 하나에 **3분 이상** 걸립니다.

더 큰 문제는 **저장되는 게 제목과 링크뿐**이라는 점입니다.
[`Notice`](../src/types/academic.ts#L17) 타입에 본문 필드가 없고, AI에게 전달하는 공지도 제목만 담습니다
([ChatPage.tsx `buildKb`](../src/pages/ChatPage.tsx#L225)).
그래서 "전과 신청 언제까지예요?" 같은 질문에 AI가 답하지 못하고, 결국 상담사 연결로 넘어와 관리자가 또 손으로 답합니다.

### 11.2 고도화 계획 — 공지 수집 자동화

1. 학교 공지를 **자동 수집**한다.
2. AI가 **카테고리·신청기간·요약**까지 구조화한다.
3. 관리자 화면에 **'승인 대기'**로 띄운다. 관리자는 확인하고 승인만 누른다.

- **입력 시간: 3분 → 10초**
- **부수 효과:** 이때 만든 요약이 그대로 AI의 지식이 된다 → AI가 공지 내용으로 답하기 시작 → 상담 문의 자체가 감소
- 관리자의 일이 **"입력하고 답변하기" → "승인하기"** 로 바뀐다

구현 시 손대야 할 지점: `Notice` 타입에 요약·신청기간 필드 추가 → `buildKb`가 요약을 함께 전송 →
승인 대기 상태를 위한 컬렉션/필드 + 관리자 앱 승인 화면.

### 11.3 그 밖의 개선 후보

- 서브 페이지(공지·검색)가 아직 테라코타 팔레트 — 홈/전화번호부의 앰버 토큰 블록을 공용 클래스로 분리 필요.
- `/search`가 UI에서 링크되지 않는 상태 — 유지할지 제거할지 결정 필요.
- `scripts/seed-data.mjs`의 `departments`는 **초안**이므로 실제 학부·학과 명칭 확인이 필요합니다.
- 미사용 레거시 CSS 정리(§10 참고).
